Ok so what is the flow of our platform. what is generated on our platform. given natural lanague what are we generating, can we provide a preview on our end? how do we integrate this with other tools

The cleanest flow is:

Natural language → robot test case → preview simulation → sensor/label/reward output → export to other tools

Your platform should not look like “we made a simulator.” It should look like:

We generate executable robot unit tests.

1. Platform flow
Step 1: User describes an edge case

Example prompt:

Generate a warehouse robot test where a mobile robot must carry a cup of water across a slippery floor while avoiding a dropped box and a human crossing the aisle.

The user can also choose:

Robot type: wheeled robot
Environment: warehouse
Sensors: RGB, depth, LiDAR
Goal: reach target zone
Success metric: water left > 70%, no collision
Export target: PyBullet, ROS, OpenPCDet, Isaac
Step 2: Your platform generates a structured scenario

The LLM turns the prompt into a scenario spec.

This is the core artifact your platform owns.

{
  "name": "slippery_cup_carry",
  "environment": {
    "type": "warehouse",
    "floor_friction": 0.25,
    "lighting": "dim"
  },
  "robot": {
    "type": "mobile_base",
    "start_position": [0, 0, 0],
    "goal_position": [5, 0, 0]
  },
  "objects": [
    {
      "id": "cup_1",
      "type": "cup",
      "position": [0.2, 0, 0.8],
      "contains": "water"
    },
    {
      "id": "box_1",
      "type": "obstacle",
      "position": [2.5, 0.3, 0.2]
    },
    {
      "id": "human_1",
      "type": "dynamic_obstacle",
      "trajectory": [[3, -1, 0], [3, 1, 0]]
    }
  ],
  "sensors": {
    "rgb_camera": true,

    }
  },

    "min_water_left_percent": 70,

    "must_reach_goal": true
  }
}

This is what you generate from natural language.

2. What is generated on your platform?

You generate a Robot Test Bundle.

Think of it like a package:

failurecloud_test/
  scenario.json
  sim_config.json
  reward_config.json
  sensors_config.json
  assets_manifest.json
  preview/
  outputs/
  exports/

Inside that bundle, you generate several things.

A. Scenario spec

This defines the world:

environment
robot
objects
hazards
materials
lighting
weather
initial positions
dynamic actors

Example:

warehouse + slippery floor + robot + cup + box + human crossing
B. Task spec

This defines what the robot is supposed to do:

start position
goal position
allowed actions
termination conditions
success conditions
failure conditions

Example:

Robot must reach the goal while keeping at least 70% water in the cup.
C. Sensor spec

This defines what data the robot collects:

RGB camera
depth camera
LiDAR/raycast sensor
collision sensor
robot pose
object poses

Example output per frame:

rgb/000001.png
depth/000001.npy
lidar/000001.npy
labels/000001.json
D. Reward/success spec

This defines RL-style evaluation.

Example:

{
  "reward": {
    "goal_progress": 1.0,
    "collision_penalty": -10.0,
    "spill_penalty": -0.5,
    "success_bonus": 20.0
  },
  "success": {
    "water_left_percent": ">= 70",
    "collisions": "== 0",
    "goal_reached": true
  }
}

For the cup example, you do not need real fluid simulation. You simulate water as a state variable:

water_left_percent = 100

Then reduce it based on:

cup tilt
robot acceleration
collisions
floor slipperiness

That is enough for a strong hackathon demo.

E. Simulator adapter files

Your platform can generate code/config for different tools.

For PyBullet MVP:

exports/pybullet/
  run_sim.py
  scenario.json
  assets/

For Isaac later:

exports/isaac/
  scene_config.yaml
  scene.usd
  task_config.json

For ROS:

exports/ros/
  topics.json
  lidar_points/
  camera_rgb/
  camera_depth/

For OpenPCDet:

exports/openpcdet/
  ImageSets/
    train.txt
  points/
    000001.npy
  labels/
    000001.txt
3. Can you provide a preview on your end?

Yes. You should absolutely provide a preview.

There are two preview levels.

Preview 1: Fast browser preview

This is the simple visual preview.

After the user types the prompt, show a 3D-ish scene in the browser:

warehouse floor
robot
cup
box
goal zone
human path
LiDAR rays

This can be done with:

Three.js
React Three Fiber
simple cubes/meshes

This preview does not need perfect physics. It is just to show:

“Here is the generated test case.”

This is useful because it gives instant feedback before simulation runs.

Preview 2: PyBullet simulation preview

This is the real MVP demo.

Backend runs PyBullet and streams/returns:

RGB frame
depth map
LiDAR points
robot state
cup tilt
water left
collision count
success/failure

In your frontend, show tabs:

Scene
RGB
Depth
LiDAR
Labels
Reward
Export

The live dashboard could show:

Status: Running
Water left: 82%
Cup tilt: 11.4°
Collisions: 0
Distance to goal: 2.1m
Reward: 37.5

At the end:

Result: FAILED
Reason: Robot reached the goal, but only 48% water remained.
Cause: High acceleration on slippery floor caused cup tilt above threshold.

This is the “wow” moment.

5. How do you integrate with other tools?

Your platform integrates through adapters.

Core idea:

scenario.json stays the same
adapters convert it into different tool formats

Architecture:

Natural language
   ↓
Scenario Compiler
   ↓
scenario.json
   ↓
Adapters
   ├── PyBullet Adapter
   ├── ROS Adapter
   ├── OpenPCDet Adapter
   ├── Isaac Adapter
   ├── CARLA Adapter
   └── Nebius/Ultimate Bots Adapter
Integration with PyBullet

This is your actual hackathon backend.

Your PyBullet adapter takes:

scenario.json

and creates:

floor
robot
cup
box
human obstacle
camera
LiDAR rays
reward loop

Then it outputs:

RGB images
depth maps
LiDAR-like point clouds
object poses
labels
reward metrics
success/failure result

This is the MVP.

Integration with ROS

ROS is for robotics stacks.

Your platform can export sensor data as ROS-style topics:

/lidar/points
/camera/rgb
/camera/depth
/tf
/robot/pose
/task/status

Even if you do not create a real .bag file during the hackathon, you can export a ROS-style folder:

ros_export/
  lidar_points.jsonl
  camera_frames/
  depth_frames/
  transforms.json
  topic_manifest.json

Pitch:

“A robotics team could replay this as if it came from robot sensors.”

Integration with OpenPCDet

Integration with Nebius / Ultimate Bots

This depends on what APIs they expose.

Your integration should be framed as:

- task

So the pitch is:

“Nebius provides the physical AI workbench. FailureCloud provides the hard tasks and evaluation layer.”
