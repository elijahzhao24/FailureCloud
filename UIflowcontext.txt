User describes a normal robot task OR exact failure case → platform generates edge-case test cases → user picks one → preview → run sim → see sensor outputs + success/failure → export.

Core UX decision

You should support two input modes, but make one the default.

Default mode: “Generate edge cases from a normal task”

This is the better product.

User says:

A robot needs to carry a cup of water across a warehouse floor.

Your platform generates edge-case tests:

1. Slippery floor
2. Dropped box blocking path
3. Human crossing aisle
4. Low lighting
5. Sudden turn causing cup spill

This is valuable because the user may not know all the edge cases. Your platform helps them think like a robotics test engineer.

Advanced mode: “Describe exact failure case”

User says:

Generate a slippery-floor scenario where the robot carries a cup, hits a dropped box, tilts the cup, and spills water.

Then your platform directly creates that test.

So the UI should say:

What do you want to test?

[ Describe a normal robot task ]
[ Describe a specific edge case ]

For the hackathon, default to normal task → generated edge cases. It feels more magical.

What are you generating?

You are generating a Robot Test Case Bundle.

Not just a scene. Not just point clouds. The generated artifact is:

RobotTestCase

It contains:

1. Scene
2. Task
3. Edge-case hazards
4. Sensor setup
5. Reward/evaluation function
6. Success/failure criteria
7. Simulation config
8. Labels
9. Export package

So yes, you are generating scenes, but more specifically:

executable robot test scenarios.

And yes, you should generate reward/loss/success definitions, but call them:

reward function
success criteria
failure criteria
evaluation metrics

“Loss function” sounds more like model training. For RL/control, “reward function” and “success metric” are cleaner.

Should the model generate success definitions?

Yes. This is one of the most important parts.

For the cup task, the model should generate:

Success:
- robot reaches goal
- water_left_percent >= 70
- collisions == 0
- time <= 30 seconds

Failure:
- water_left_percent < 70
- cup dropped
- collision with obstacle
- timeout

Reward:

+ progress toward goal
- spill amount
- collision
- excessive tilt
+ success bonus

In the UI, show it as editable sliders:

Minimum water left: [70%]
Max collisions: [0]
Timeout: [30s]
Spill penalty: [-0.5]
Collision penalty: [-10]
Success bonus: [+20]

This is a strong feature because most simulation platforms do not magically write your task/evaluator for you.

Should you generate scenes?

Yes, but phrase it carefully.

You are not generating photoreal worlds from scratch.

You are generating:

That is the right framing.

Final answer

The UX should not start with “generate a point cloud.”

It should start with:

What robot task do you want to test?

Then your platform says:

Here are the dangerous edge cases. Pick one. I’ll generate the scene, sensors, labels, reward function, success criteria, run the sim, and export the test.
